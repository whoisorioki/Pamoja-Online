## The Source of Truth Is Authoritative

Hard requirements (detail in the SOT, not here):

- **No real-identity accounts.** Token is a client-generated three-word
  phrase in `localStorage`.
- **No public forum.** Two passphrase-gated spaces: `mens` and `womens`.
- **No leaderboards, ranks, or public reputation.**
- **No custom backend server.** Frontend talks to Supabase. Never
  FastAPI, Railway, or an app server "just for this."
- **Only the Supabase `anon` key** may appear in frontend or build env.
  `service_role` must never appear in any file in this repo.
- **RLS before wiring.** Do not ship a table, or a form that writes to
  one, without a tested RLS policy (cross-token and cross-space).
- **One template + `sessions.json`** for week pages. Do not duplicate
  week HTML.
- **Sharing is explicit.** Never default a journal entry onto the forum.

If a human instruction conflicts with the SOT, flag the conflict before
writing code.

## Design conventions (when building UI)

- 12px corner radius on cards, site-wide.
- One primary action per screen. Secondary actions get equal weight,
  never ranked against each other.
- Calm, warm tone — not competitive or gamified.
- Shneiderman's Eight Golden Rules: SOT Section 5. Do not invent a
  second visual system.

## What to Do When Unsure

Stop and ask before writing code if:

1. The SOT and implementation plan are silent on the decision.
2. You would add a new Supabase table, column, or RLS policy that is
   not in SOT §8.
3. You would put `service_role`, a real name/email, or an IP log
   anywhere in the repo.
4. You would introduce a bundler, framework, or backend not listed in
   SOT §6.1.
5. You would change curriculum content without editing
   `src/_data/sessions.json` as the single source.
6. You would add a tool-specific agent file that duplicates this one.
